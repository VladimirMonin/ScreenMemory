# DOCS — Коммиты ScreenMemory

## Границы применения

Правила согласованы с [master v3, §16](../docs/ScreenMemory_Full_Development_Plan_v3.md#workflow).
При создании этой инструкции Git-репозитория и исходников в ScreenMemory ещё нет.
Не выполняй commit/init/clone вместо запрошенной вычитки документов.
Подготовка истории с сохранением происхождения Inspector — отдельный шаг старта.

В существующем Git-репозитории агент с разрешением на реализацию фиксирует каждый
завершённый проверенный логический срез локальным commit, если пользователь не
попросил оставить изменения незакоммиченными. Не спрашивай заново «один или несколько»:
группируй по смыслу. Read-only работа не разрешает staging/commit.
При делегировании staging/commit выполняет основной интегратор, не leaf-worker/reviewer.

## Формат сообщения

```text
<prefix>(<scope>): <Краткое название изменения по-русски>

- Завершённое изменение поведения или контракта
- Существенная защита, проверка или ограничение

Stage: S01
Task: S01-T04
Requirements: OPS-01
Tests: S01-LOG-01, S01-VER-01
Verification: <реальные команды/результаты либо путь к отчёту>
Migration: <изменение схемы/восстановление либо none>
```

Это шаблон, не отчёт о выполнении перечисленных тестов. Поля Stage/Task/Requirements/
Tests заполняй действительными ID, когда срез реализует этап; для организационной
docs-задачи не изобретай requirement или task ID. Verification обязателен.
Migration нужен при изменении данных; пустые формальные блоки не добавляй.

Допустимые префиксы: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`,
`build`, `ci`, `perf`, `revert`. `revert` как тип сообщения не даёт разрешения
выполнять откат. Для исправлений используй `fix` по Conventional Commits.
Scope отражает владельца,
например `foundation`, `capture`, `storage`, `runtime`, `search`, `instructions`.

Заголовок и тезисы разделяй пустой строкой. Обычно достаточно 2–5 тезисов;
не растягивай тривиальное исправление до искусственного списка. Для многострочного
русского сообщения используй UTF-8 файл и `git commit --file <file>` с настоящими
переводами строк; временный файл сообщения в commit не включай.

## Смысловая атомарность

Один commit — одна проверяемая логическая задача, не один файл и не весь этап.
Контракт, код, релевантные тесты и обновление инструкции одной фичи идут вместе.
Не смешивай несвязанные UI-правки, migration и массовое переименование.
Не включай чужую незавершённую работу даже при общем пути файла.

По умолчанию коммитится завершённый зелёный срез. Master §16.4 отдельно допускает
временные красные TDD-коммиты **в рабочей ветке**: ожидаемый падающий тест явно
обозначается, регрессия не скрывается, такой commit не становится accepted checkpoint.
Это не разрешение объявлять незаконченную работу готовой или игнорировать новые ошибки.

## Preflight и staging

1. Проверь repo root, branch/worktree, `git status --short` и исходный diff.
2. Прочитай затронутые инструкции; проверь scope и отсутствие чужих изменений.
3. Выполни проверки ниже; запиши команды, cwd, raw exit codes и пропуски.
4. Просмотри полный diff, включая новые файлы. Исключи секреты, `.env`, личные
   изображения, БД, логи, веса, кеши, сборки и временные артефакты.
5. Используй явные пути в `git add -- <paths>` или точные hunks. Не применяй
   без разбора `git add .` / `git add -A` в общем рабочем дереве.
6. Проверь `git diff --cached`, `git diff --cached --check` и staged file list.
   Важные проектные отчёты допустимы, только если это согласованные deliverables
   без чувствительных данных; сырые runtime-логи автоматически не добавляются.
7. После commit проверь его состав, точный SHA и оставшийся status. Не требуй
   очистить всё дерево ценой потери независимых изменений.

## Проверки до принятого commit

**Только документация:** ссылки и пути, YAML инструкций, каталог AGENTS.md,
согласованность терминов/статусов и SHA-256 зависимых планов. При наличии Git —
`git diff --check` и проверка staged diff. Не запускай отсутствующие build scripts
и не записывай их отсутствие как успешный тест.

**Код после bootstrap:** сначала проверь реальные Cargo/pnpm manifests, lockfiles
и scripts. Плановые базовые команды master:

| Область | Проверка после появления соответствующей инфраструктуры |
|---|---|
| Rust | `cargo fmt --all -- --check` |
| Rust | `cargo clippy --workspace --all-targets --locked -- -D warnings` |
| Rust | Релевантные тесты; `cargo test --workspace --locked` для общего gate |
| TypeScript / frontend / bridge | `pnpm typecheck`, `pnpm lint`, релевантные `pnpm test` |
| Контракты / Windows / runtime | Реальные verification scripts и gates текущего этапа |

Названия pnpm-команд и wrapper пока целевые: S01 должен их создать и проверить.
Dependency install — отдельный bootstrap с locked versions, не скрытая часть docs-check.

Обязательная упавшая проверка блокирует принятие среза. Исправь ошибку либо явно
отдели подтверждённый baseline blocker; не отключай тест/правило ради зелёного статуса.
Точечное подавление требует конкретного правила и причины, широкие suppressions запрещены.
Не полагайся на наличие hooks: их конфигурация здесь пока не установлена.

Сохраняй **сырой exit code каждого процесса**. `tail`, фильтры и успешный последний
шаг pipeline не доказывают успех предыдущего. `NOT_RUN`/`BLOCKED` не равны `PASS`.
Локальный code commit с недоступным live-gate не становится принятым этапом/релизом:
пропущенный gate и требуемая среда остаются явно перечисленными в отчёте.

## Деструктивные и удалённые операции

Без отдельного явного разрешения запрещены `git revert`, `reset --hard/--mixed`,
`clean -fd`, откат целых файлов через `checkout --` / `restore`, переписывание
истории и `commit --amend`. Для baseline не прячь чужие изменения в stash:
используй отдельный чистый checkout/worktree. Не удаляй чужие ветки/worktrees.

Push, force-push, удаление remote branches, создание удалённого fork, tags/release
и публикация не следуют из разрешения на локальный commit. Push — только по явному
запросу пользователя. Force-push в `main`/`master` запрещён. Рабочую branch/release
схему и нумерацию версий ScreenMemory зафиксируй при bootstrap.

В итоговом отчёте сообщи SHA, проверки и оставшиеся ограничения. Если Git ещё нет
или commit не выполнялся, скажи это прямо; не создавай вымышленную контрольную точку.

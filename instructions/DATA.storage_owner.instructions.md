# DATA — SQLite owner foundation

`sm-storage` — единственный владелец production SQLite connection: выделенный worker получает **потреблённый** `HostLease` и удерживает его до закрытия connection. `sm-application::storage` предоставляет только typed snapshots/errors; никакого SQL, raw connection или DB path в application/GUI/CLI/async handler. Команды в bounded queue, overload/timeout — `Unavailable`, не «Stopped». Успешный stop acknowledgement допускается только **после** close connection, освобождения pinned DB entries и lease. Перед любым open — настоящий lock и preflight; см. [root isolation](INFRA.root_isolation.instructions.md).

Фиксированный `data/library.sqlite3`, защищённые `-wal`, `-shm`, `-journal` проверяются на reparse/directory/hardlink/volume и удерживаются; никакого произвольного path-write authority. Root — локальный NTFS, не сеть; не sandbox против злонамеренного same-user/admin. Изменение этих native проверок требует синтетического NTFS negative proof. Никаких live libraries в тестах: только собственные уникальные `.pi/temporary` fixtures, без user ACL/global setup; test fixture удаляется только после успешного завершения работы worker.

`0001_foundation.sql` (library_meta, library_settings) и bootstrap schema_migrations в **одной** транзакции вместе с migration row/seeds. Checksum — SHA-256 shipped SQL bytes. Библиотечный UUID создаётся один раз. Existing DB: до SQLite-open сначала сверяется durable own-init marker основного файла; отсутствие marker (включая существующие пустые/нулевые SQLite, чужие после DROP/VACUUM) — отказ без adoption и без побочных sidecars. Только новый path без sidecars под lease получает marker до WAL и миграционной транзакции. После этого read-only compatibility preflight (реальный WAL, не immutable-read) допускает owned schema-empty DB или owned корректную пустую bootstrap migration table после interruption, а также валидную foundation schema. Marker не является sandbox/auth для злонамеренного same-user; совпадение marker без schema validation недостаточно. Unknown schema, future version, migration mismatch, испорченные UUID/settings/schema отвергаются без repair/delete/adoption. Destructive upgrades только после проверенного backup; S08 backup/restore пока не реализованы. Канон/staging поздних стадий — source of truth, не disposable cache. `ai.enabled=false`, `model.autostart=false`; только валидированная typed schema, никаких произвольных endpoints, секретов или свободного key/value API. Новые settings/миграции — отдельное согласование, с тестами отката и совместимости.

S02 добавляет `0002_images.sql` (`records`/`assets`, закрытый словарь `webp_lossless` и `original|preview|edited`), применяется тем же migrator’ом в одной транзакции и регистрируется как версия 2; `SchemaSnapshot.images` сообщает применённую версию и канонический формат. Канонический файл пишет только этот writer: запись record + asset + файла идёт в одном `BEGIN IMMEDIATE`, а откат удаляет ровно свой файл. `0003_operations.sql` добавляет durable `ingest_operations` (глобальная таблица, applied version 3, images contract остаётся 2): закрытый `mode` (`region|active_window|monitor|desktop` — typed-имена `CaptureTarget`, а не wire-алиасы), положительные `width`/`height` (потолок 16383) и bounded JSON `warnings`; строка `saved` пишется тем же `BEGIN IMMEDIATE` вместе с record/asset/файлом, никогда частично. Replay lookup — ownership-scoped и typed: только собственный principal и совпадающий mode дают `Saved` с receipt metadata; чужой principal и смена mode — один и тот же безопасный `Conflict` **без** metadata; `Unknown` — только действительно отсутствующий ID. Сохранённый mode сравнивается с запрошенным по сырому тексту строки **до** разбора остальных metadata, поэтому несовпадающий mode остаётся тем же `Conflict` даже при повреждённых warnings или отсутствующем joined asset. Повреждённая `saved`-строка/asset — ошибка, а не выдуманный receipt: и replay своего совпадающего operation, и повторный публичный `commit_image_capture` с совпавшим semantic fingerprint проверяют канонический файл (существование, размер, SHA-256, safe relative path) до выдачи `Saved`, а объявленный размер ограничен `MAX_CANONICAL_FILE_BYTES` до любого IO; отсутствие/подмена файла — typed integrity failure (`IntegrityFailed`/`AssetIntegrityFailed`), oversized — отказ по metadata length без чтения. Canonical MIME восстанавливается из проверенного `a.format`, warnings/размеры — из журнала, не из новой съёмки. Codec и images-типы — `sm-codec` и `sm-application::storage`; `sm-codec` не имеет доступа к FS/сети/логам. Проверки текущего subset: `scripts/verify.ps1` (`STORAGE-FOUNDATION`, `TESTS-CODEC`, `TESTS-STORAGE-IMAGES` плюс workspace), `scripts/verify-contracts.ps1` (boundary), тесты `s01_db_01*`, `s01_db_02*`, `s02_images_*`, `s02_t09a_13*`…`s02_t09a_31*`; сохранять raw exits, PRE/POST plan/source и приватные логи только под `.pi/`. S02-T09m1: `0004_capture_intents.sql` регистрируется как глобальная SHIPPED migration v4, не меняя immutable 0001–0003 и `SchemaSnapshot.images.migration_version=2`. Отдельная `capture_intents` хранит только pending identity и проверяемые будущие intent-поля (canonical lowercase hyphenated non-nil UUID для operation/principal любого version/variant; UUIDv4 для planned record/asset/frame; mode, geometry/pixel cap, lower-case SHA-256 digests, bounded JSON context/warnings, fingerprint, canonical-length timestamps); FK связывает `library_id` с `library_meta`. Двусторонние SQL triggers запрещают один `operation_id` одновременно в pending и saved journal; будущий writer должен удалить pending до вставки saved **в том же** `BEGIN IMMEDIATE`, и только после проверенного канона. v4 сама по себе не создаёт pending rows и не меняет существующий Saved commit. S02-T09m2 добавляет только typed `FoundationRepository::{create_capture_intent,read_capture_intent}` на bounded SQLite worker channel: trusted library/principal/real `CaptureRequest` (mode+trigger), заранее выделенные v4 record/asset/frame, geometry, validated bounded context/warnings, lowerhex pixel SHA-256 и профиль. Domain-separated request fingerprint вычисляется worker из текущего запроса, не приходит извне; create в `BEGIN IMMEDIATE` сначала проверяет Saved без проекции metadata и возвращает безопасный `Conflict`, затем проверяет scoped pending, identical → `Existing`, собственный тот же request с другим caller content/IDs после проверки хранимой строки → безопасный `Conflict`, unknown → `Created`. SQLite UTC `planned_created_at_utc` создаётся только при новой вставке внутри транзакции; никакой manifest timestamp не принимается. Read чужого principal/изменённого mode возвращает без metadata `Conflict` даже при повреждённом fingerprint; совпадающие principal/mode и другой реальный закрытый trigger → `Conflict`, но fingerprint, не соответствующий ни Hotkey, ни ClientCommand для сохранённых operation/mode → `IntegrityFailed`. Отсутствие → `Unknown`, собственная строка проверяется повторно (включая context digest); повреждение → `IntegrityFailed`, без repair/delete. Эти состояния НЕ являются `Saved` или durable input; прежний `lookup_operation` pending не видит. Host wiring, startup reconciliation, retry/status и process-kill/RSS доказательства — **NOT_WIRED/NOT_RUN**. Синтетические миграционные тесты проверяют v3→v4, rollback/checksum, ограничения/FK/collision; SQL JSON guards — граница, не замена будущей typed validation.

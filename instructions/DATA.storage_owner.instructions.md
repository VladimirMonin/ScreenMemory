# DATA — SQLite owner foundation

`sm-storage` — единственный владелец production SQLite connection: выделенный worker получает **потреблённый** `HostLease` и удерживает его до закрытия connection. `sm-application::storage` предоставляет только typed snapshots/errors; никакого SQL, raw connection или DB path в application/GUI/CLI/async handler. Команды в bounded queue, overload/timeout — `Unavailable`, не «Stopped». Успешный stop acknowledgement допускается только **после** close connection, освобождения pinned DB entries и lease. Перед любым open — настоящий lock и preflight; см. [root isolation](INFRA.root_isolation.instructions.md).

Фиксированный `data/library.sqlite3`, защищённые `-wal`, `-shm`, `-journal` проверяются на reparse/directory/hardlink/volume и удерживаются; никакого произвольного path-write authority. Root — локальный NTFS, не сеть; не sandbox против злонамеренного same-user/admin. Изменение этих native проверок требует синтетического NTFS negative proof. Никаких live libraries в тестах: только собственные уникальные `.pi/temporary` fixtures, без user ACL/global setup; test fixture удаляется только после успешного завершения работы worker.

`0001_foundation.sql` (library_meta, library_settings) и bootstrap schema_migrations в **одной** транзакции вместе с migration row/seeds. Checksum — SHA-256 shipped SQL bytes. Библиотечный UUID создаётся один раз. Existing DB: до SQLite-open сначала сверяется durable own-init marker основного файла; отсутствие marker (включая существующие пустые/нулевые SQLite, чужие после DROP/VACUUM) — отказ без adoption и без побочных sidecars. Только новый path без sidecars под lease получает marker до WAL и миграционной транзакции. После этого read-only compatibility preflight (реальный WAL, не immutable-read) допускает owned schema-empty DB или owned корректную пустую bootstrap migration table после interruption, а также валидную foundation schema. Marker не является sandbox/auth для злонамеренного same-user; совпадение marker без schema validation недостаточно. Unknown schema, future version, migration mismatch, испорченные UUID/settings/schema отвергаются без repair/delete/adoption. Destructive upgrades только после проверенного backup; S08 backup/restore пока не реализованы. Канон/staging поздних стадий — source of truth, не disposable cache. `ai.enabled=false`, `model.autostart=false`; только валидированная typed schema, никаких произвольных endpoints, секретов или свободного key/value API. Новые settings/миграции — отдельное согласование, с тестами отката и совместимости.

`rusqlite` bundled/exact и `Cargo.lock` закреплены; foreign_keys=ON, WAL, synchronous=FULL, busy_timeout=5000 проверяются readback. Static sqlite-vec registration seam относится к будущему T09, здесь запрещены произвольные load_extension и фиктивный vec PASS. S02 добавляет `0002_images.sql` (`records`/`assets`, закрытый словарь `webp_lossless` и `original|preview|edited`), применяется тем же migrator’ом в одной транзакции и регистрируется как версия 2; `SchemaSnapshot.images` сообщает применённую версию и канонический формат. Канонический файл пишет только этот writer: запись record + asset + файла идёт в одном `BEGIN IMMEDIATE`, а откат удаляет ровно свой файл. `0003_operations.sql` добавляет durable `ingest_operations` (глобальная таблица, applied version 3, images contract остаётся 2): закрытый `mode` (`region|active_window|monitor|desktop` — typed-имена `CaptureTarget`, а не wire-алиасы), положительные `width`/`height` (потолок 16383) и bounded JSON `warnings`; строка `saved` пишется тем же `BEGIN IMMEDIATE` вместе с record/asset/файлом, никогда частично. Replay lookup — ownership-scoped и typed: только собственный principal и совпадающий mode дают `Saved` с receipt metadata; чужой principal и смена mode — один и тот же безопасный `Conflict` **без** metadata; `Unknown` — только действительно отсутствующий ID. Сохранённый mode сравнивается с запрошенным по сырому тексту строки **до** разбора остальных metadata, поэтому несовпадающий mode остаётся тем же `Conflict` даже при повреждённых warnings или отсутствующем joined asset. Повреждённая `saved`-строка/asset — ошибка, а не выдуманный receipt: и replay своего совпадающего operation, и повторный публичный `commit_image_capture` с совпавшим semantic fingerprint проверяют канонический файл (существование, размер, SHA-256, safe relative path) до выдачи `Saved`, а объявленный размер ограничен `MAX_CANONICAL_FILE_BYTES` до любого IO; отсутствие/подмена файла — typed integrity failure (`IntegrityFailed`/`AssetIntegrityFailed`), oversized — отказ по metadata length без чтения. Canonical MIME восстанавливается из проверенного `a.format`, warnings/размеры — из журнала, не из новой съёмки. Codec и images-типы — `sm-codec` и `sm-application::storage`; `sm-codec` не имеет доступа к FS/сети/логам. Проверки текущего subset: `scripts/verify.ps1` (`STORAGE-FOUNDATION`, `TESTS-CODEC`, `TESTS-STORAGE-IMAGES` плюс workspace), `scripts/verify-contracts.ps1` (boundary), тесты `s01_db_01*`, `s01_db_02*`, `s02_images_*`, `s02_t09a_13*`…`s02_t09a_31*`; сохранять raw exits, PRE/POST plan/source и приватные логи только под `.pi/`. S02-T09m1: `0004_capture_intents.sql` регистрируется как глобальная SHIPPED migration v4, не меняя immutable 0001–0003 и `SchemaSnapshot.images.migration_version=2`. Отдельная `capture_intents` хранит только pending identity и проверяемые будущие intent-поля (canonical lowercase hyphenated non-nil UUID для operation/principal любого version/variant; UUIDv4 для planned record/asset/frame; mode, geometry/pixel cap, lower-case SHA-256 digests, bounded JSON context/warnings, fingerprint, canonical-length timestamps); FK связывает `library_id` с `library_meta`. Двусторонние SQL triggers запрещают один `operation_id` одновременно в pending и saved journal; будущий writer должен удалить pending до вставки saved **в том же** `BEGIN IMMEDIATE`, и только после проверенного канона. v4 сама по себе не создаёт pending rows и не меняет существующий Saved commit. S02-T09m2 добавляет только typed `FoundationRepository::{create_capture_intent,read_capture_intent}` на bounded SQLite worker channel: trusted library/principal/real `CaptureRequest` (mode+trigger), заранее выделенные v4 record/asset/frame, geometry, validated bounded context/warnings, lowerhex pixel SHA-256 и профиль. Domain-separated request fingerprint вычисляется worker из текущего запроса, не приходит извне; create в `BEGIN IMMEDIATE` сначала проверяет Saved без проекции metadata и возвращает безопасный `Conflict`, затем проверяет scoped pending, identical → `Existing`, собственный тот же request с другим caller content/IDs после проверки хранимой строки → безопасный `Conflict`, unknown → `Created`. SQLite UTC `planned_created_at_utc` создаётся только при новой вставке внутри транзакции; никакой manifest timestamp не принимается. Read чужого principal/изменённого mode возвращает без metadata `Conflict` даже при повреждённом fingerprint; совпадающие principal/mode и другой реальный закрытый trigger → `Conflict`, но fingerprint, не соответствующий ни Hotkey, ни ClientCommand для сохранённых operation/mode → `IntegrityFailed`. Отсутствие → `Unknown`, собственная строка проверяется повторно (включая context digest); повреждение → `IntegrityFailed`, без repair/delete. Эти состояния НЕ являются `Saved` или durable input; прежний `lookup_operation` pending не видит. Host wiring, startup reconciliation, retry/status и process-kill/RSS доказательства — **NOT_WIRED/NOT_RUN**. Синтетические миграционные тесты проверяют v3→v4, rollback/checksum, ограничения/FK/collision; SQL JSON guards — граница, не замена будущей typed validation.

S02-T09b вводит только чистый validator стадии: `crates/storage/src/staging.rs` `validate_staging(manifest <=64 KiB, context <=256 KiB, borrowed RGBA, StagingExpectations)` принимает только доверенные library/principal/operation/mode/profile, требует schema version 1, fixed `capture`/`staged`, канонические не-nil UUID, checked `stride=width*4` и `byte_length=stride*height`, потолки `MAX_CAPTURE_SIDE`/`MAX_CAPTURE_PIXELS` из `sm-application::capture`, exact SHA-256 пикселей/context, canonical timestamp, согласованные `CaptureContext::from_json` bounds/target, и отвергает дублирующиеся, неизвестные и любые path-like поля. Он не выполняет никакого FS/SQL/wire IO, не создаёт staging-папку, не пишет manifest и **NOT_WIRED** к host/bootstrap/recovery: `durable_input`/публикация manifest не существуют, а `staged` в manifest — документируемая граница, не durable receipt. Тесты `s02_t09b_01*`…`s02_t09b_12*` и boundary-проверка чистоты модуля; F02–F05 recovery/publish остаются отдельными будущими срезами. Actual inaccessible ACL path probe без разрешённых ACL изменений помечать NOT_RUN, не заменять IO sharing denial. См. [ADR-004](../docs/adr/004-storage-worker.md).

S02-T09b добавляет файловый координатор стадии `crates/storage/src/staging_files.rs`. `stage_capture(borrowed StagingRoot, StageInput)` принимает **только** доверенные typed-входы (library/principal/operation/record/asset/frame UUID, typed mode, re-validated `CaptureContext`, canonical capture time, trusted encoder fingerprint и borrowed packed RGBA) — ни пути, ни имени файла. Он строит ровно 18-полевой v1 manifest (<=64 KiB) и context (<=256 KiB), считает SHA-256 по borrowed-срезам и пропускает триплет через тот же чистый `validate_staging` **до** первой записи; несогласованный вход не создаёт operation directory. Затем под заимствованным lease-полномочием: `create_operation` → `pixels.rgba.tmp` → sync → publish `pixels.rgba` → `context.json` → sync → publish → `manifest.json` sync и **публикуется последним**. `Staged` возвращается только после всех публикаций, но остаётся границей файловой записи, а не host `Saved`, не durable-input флагом и не обещанием power-loss durability. `reopen_staged(borrowed root, StagingExpectations)` читает только фиксированные имена bounded/no-follow чтением и снова проверяет manifest тем же `validate_staging(expected trusted identity/profile)`; чужой/повреждённый/усечённый опубликованный артефакт — typed `Rejected`, отсутствующий manifest/operation — отдельный `Incomplete`, и **никакие** файлы не удаляются (temp, unknown/sentinel остаются). Существующий, но превысивший schema-потолок артефакт (`TooLarge` от lease) никогда не превращается в ложное отсутствие: manifest — `Rejected(ManifestBeyondLimit)`, context — `Rejected(ContextBeyondLimit)`, pixels — `Rejected(PixelLengthMismatch)`; `MissingArtifact` остаётся только для действительно отсутствующего fixed-файла. Детерминированные failpoints (F02 середина pixels.tmp, F03 оба stable до manifest, F04 manifest опубликован) живут только в test-seam внутри crate; production всегда `StageSeams::NONE`. Tests `s02_t09b_13*`…`s02_t09b_21*` и boundary-проверка: модуль не имеет `std::fs::`/path/SQL/wire/process и не публикует `durable_input`/`Saved`. В T09b primitive вызывался только из isolated test на синтетическом `.pi/temporary` NTFS root; F05–F10 recovery/publish остаются будущими срезами.

S02-T09h: отдельный чистый `validate_recovery_envelope` (`crates/storage/src/staging.rs`) принимает только bounded manifest <=64 KiB, context <=256 KiB и borrowed RGBA с доверенными `StagingExpectations`. v1 остаётся строго прежним 18-полевым `validate_staging`: версия 1 корректна как staged input, но **не recovery-ready**, потому что точные receipt warnings неизвестны; нельзя трактовать их как пустой список или восстанавливать задним числом. Только закрытый 21-полевой v2 с обязательным typed `warnings` (тот же application warnings codec), `provenance_kind=automatic` (when из captured_at, source из context.target) и `path_policy=commit_month_record_original_v1` (текущий layout, без входного path), после полной проверки identity/mode/profile/geometry/hash/context/timestamp помечается recovery-ready **на уровне supplied bytes**. S02-T09i добавляет изолированные `stage_capture_v2` и `reopen_staged_v2` в `staging_files.rs`: доверенный `StageInputV2` с точными упорядоченными warnings собирает закрытый 21-полевой manifest и проходит чистый validator **до** создания operation; прежний v1 writer/reopen не меняется. V2 использует ту же manifest-last последовательность фиксированных no-replace файлов; reopen отдаёт проверенный envelope **и owned RGBA bytes** из bounded/no-follow чтения, v1 без warnings отвергает, чужой/повреждённый input не чинит и не удаляет. На границе T09i это были только изолированные NTFS тесты без host/file lane. T09j подключает **новые** command и hotkey captures к отдельному owned v2-запросу того же scoped file lane/lease: exact ordered warnings проверяются до записи, manifest публикуется последним, host сверяет schema2/IDs/context/freeze provenance/profile/path policy/warnings до encode и DB commit; legacy v1 API остаётся, но production не создаёт новые v1 stage. `Saved` возникает только после нынешнего verified canonical и DB commit, не из `is_recovery_ready()` или наличия v2 manifest. SQL schema/status/retry/startup reconciliation **NOT_WIRED**; power-loss durability не доказана. v1 файлы без точных warnings требуют отдельного решения/вмешательства. T09k добавляет `StorageWorker::reopen_stage_owned_v2`: доверенные owned library/principal/operation, typed mode и bounded encoder fingerprint без path проходят через тот же bounded file lane и заимствованный исходный HostLease; только полностью проверенный v2 возвращает `ReopenedV2` с приватным envelope и пикселями, доступными лишь по immutable borrow. Отсутствующий manifest/operation — `Incomplete`, legacy v1, foreign/unsafe/corrupt/oversize — typed отказ без выдачи metadata и без удаления; admission gate закрывается перед Stop, принятые Stage/Probe/Reopen FIFO дренируются до release lease. Synthetic NTFS тесты `s02_t09k_*` проверяют reopen после shutdown/reacquire нового worker, не создавая DB receipt. Startup enumeration, SQL recovery/retry/status, codec и process-kill F04–F10 остаются будущими срезами; power-loss durability не доказана.

S02-T09l2 подключает только `StorageWorker::enumerate_stage_candidates()` — path-free async discovery возвращает bounded `StagingCandidates` с **недоверенными** IDs и счётчиками или typed `EnumerateCandidatesError` (`Unavailable` при закрытом gate/full/disconnect/cancelled response, `Enumeration(StagingError)` при отказе root/scan). Отдельный `FileRequest::EnumerateCandidates` обрабатывается на прежнем scoped file lane из borrowed исходного HostLease, с тем же `sync_channel(1)`, admission gate и FIFO Stop/join; в SQLite loop, host и startup scan не выполняется. Уже принятый запрос выполняется даже после отмены waiter; при ошибке никогда не возвращать пустой список как успех. Потолок 4096 non-dot entries остаётся во владельце `sm-isolation`; discovery не принимает manifest, не удаляет файлы, не сверяет SQL receipt, не создаёт статус/retry и не гарантирует snapshot при внешних конкурентных изменениях. Synthetic tests `s02_t09l2_*` отдельно проверяют reacquire, incomplete и sentinel, DB `Unknown`, v2 reopen, full/closed gate и Stop с удержанием lease. Recovery orchestration, adoption и power-loss proof остаются NOT_WIRED.

T09d identity seam: host для command после DB Saved replay, при `Unknown` — после fail-closed `probe_stage_presence`, и после admission, но **до native freeze**, один раз выделяет доверенные operation (из запроса), record/asset/frame (UUIDv4). Для hotkey IDs выделяются один раз только после принятого native outcome, перед прежним verified commit. `commit_command` использует заранее выделенные record/asset, не создаёт повторно IDs; frame ID пока хранится только в host identity, не в DB/`CommitImageCapture`. Ни stage-вызов, ни host-owned save task/recovery, ни durable-input этим seam не подключены. Существующий `Saved` по-прежнему только после verified canonical и DB commit.

T09c: `StorageWorker::stage_capture_owned` принимает только owned trusted IDs/context/profile/time и один `Vec<u8>` packed RGBA, без path/filename. Предварительно проверяются checked geometry/длина, bounded context/profile/time; владелец файла — отдельный bounded `sync_channel(1)` + scoped child, заимствующий **исходный** lease. В SQLite worker stage IO не выполняется; общий admission gate закрывает запросы обоих каналов перед Stop, file Stop следует после всех принятых Stage. При отмене waiter уже принятый staging выполняется, не удаляется; перегрузка/timeout — `Unavailable`, не `Stopped`. Успешный shutdown разрешён только после SQLite close, FIFO file drain + join и drop lease; после timeout explicit retry возможен. Staged — только файл, не DB journal/host Saved/durable_input. Поддержка host и recovery остаётся отдельной задачей; ограничена лишь очередь 1 pending + 1 executing, не общий RAM budget вызывающих. Synthetic NTFS test `file_lane_tests.rs` и `tests/contracts/check_boundaries.py` проверяют границу.

# INFRA — Root isolation до host

`sm-isolation` — единственный текущий владелец identity продукта/окружения и read-only Windows resolver. Installed configuration явно содержит существующие четыре каталога `ScreenMemory[.Dev|.Test]/{data,config,cache,webview}` и явно известные forbidden donor roots; test требует explicit root с четырьмя заранее созданными дочерними каталогами. Ни CWD, ни home, ни PATH не используются как fallback. Не считывать реальные settings/history/credentials Inspector для поиска donor roots. Если известный forbidden root не разрешается, отказ, не исключение из проверки. Никаких изменений существующих папок resolver не делает.

`HostLease::acquire` потребляет `NamespaceLayout` с удерживаемыми root/ancestor handles и открывает постоянный `data/host.lock` с немедленным exclusive byte-range OS lock до любых будущих SQLite writes. Locked handle закрывается раньше pinned root chain; guard не Clone, при drop lock-файл не удаляется и содержимое не интерпретируется как PID. Busy не даёт права kill/recover чужой host; отсутствие IPC не снимает OS lock. Resolver сам по себе не выдаёт разрешения на SQLite writes, не создаёт каталогов и не очищает непустые данные. Foundation migration/SQLite worker реализованы отдельным кандидатом T05b, см. [DATA.storage_owner](DATA.storage_owner.instructions.md); backup/production host lifecycle ещё не реализованы. Канон и принятый staging — protected source of truth; test roots — только `.pi/temporary` со строго синтетическими sentinel bytes, имена root fixture — UUIDv4 (не PID+wall-clock); atomic create_dir collision отказывает без adoption/delete, guard удаляет только собственную успешно созданную fixture после проверок. Не распространять test cleanup на живой каталог, не обещать физическое удаление на SSD. Backup/integrity/hash/restore policy для persistent data определит будущий storage owner до первой записи; отсутствие проверенного backup означает отказ в потенциально разрушительной миграции. Никаких автозапусков updater, donor shell или чужих сервисов.

`windows.rs` изолирует Win32 SDK ABI: local fixed NTFS, каждый ancestor и leaf открываются с `FILE_LIST_DIRECTORY|FILE_READ_ATTRIBUTES`, `OPEN_REPARSE_POINT|BACKUP_SEMANTICS`, без FILE_SHARE_DELETE, удерживаются на lifetime layout/lease; metadata-only `FILE_READ_ATTRIBUTES` **не удерживает rename** (synthetic RED T05a), поэтому менять access обратно нельзя; после закрепления всей цепочки повторная проверка каждого prefix по volume/file identity отвергает initial swap. Конфликт с уже открытым DELETE handle отвергается. `host.lock` открывается внутри удерживаемого root с `OPEN_REPARSE_POINT` и без DELETE share, rejects directory/reparse/multi-hardlink, не unlink/truncate. Эта проверенная на synthetic NTFS комбинация защищает от обычных rename/reparse races, **не** sandbox против процесса того же пользователя/admin и не разрешение на произвольные path-based writes внутри root. Directory identity и полный путь внутренние, не DTO/status/обычные логи. `HostLease::staging_root()` — borrowed authority оригинального lease, а не передаваемая из bootstrap копия; только фиксированный sibling `staging` от pinned `data` на том же локальном NTFS. `StagingRoot::create_operation(OperationId)` принимает non-nil UUID, атомарно создаёт новый каталог и pin/validates цепочку; `StagingOperation::create_temp` ограничен тремя именами `pixels.rgba.tmp`, `context.json.tmp`, `manifest.json.tmp` и выдаёт tied `Write`/`sync_all` handle с CREATE_NEW/no-follow/no-overwrite. Существующие reparse entries и повторные операции/файлы не перезаписывать и не удалять неизвестные файлы. Следующий файловый capability-срез: `open_operation(non-nil OperationId)` повторно закрепляет существующий каталог без adoption/cleanup; `StagingTemp::publish` доступен только после успешного `sync_all` без последующих записей и явно публикует фиксированное stable-имя (включая отдельный шаг вызова для manifest). `open_fixed` возвращает проверенный no-reparse, same-volume, single-link handle с ограниченным чтением (pixels 512 MiB, context 256 KiB, manifest 64 KiB); это потолки capability, не валидация содержимого/размеров изображения. `MoveFileExW` вызывается только с `MOVEFILE_WRITE_THROUGH`, без COPY_ALLOWED/REPLACE_EXISTING; до и после перехода сверяются source/destination identity. Между закрытием исходного handle и pathname-based rename остаётся гонка с враждебным процессом того же пользователя, который заранее получил DELETE-доступ; это не sandbox. Публикация manifest сама по себе **не** устанавливает `durable_input`: schema/hash/recovery, durable receipt и host/storage wiring **ещё не выполнены**. Не объявлять staging принятой только по вызову публикации. Synthetic NTFS tests — `crates/isolation/tests/staging.rs`; staging и канон не disposable cache. `StagingRoot::enumerate_candidates(&self)` — только read-only discovery из pinned staging directory HANDLE: полный restart-to-EOF scan сериализован приватным mutex данного root (poison → `EnumerationIncomplete`), native class 15/14 с разбором всех записей каждого batch, потолок 4096 non-dot entries (до 4099 native queries с учётом `.`/`..` и EOF); 4097-я non-dot запись, ошибка или невозможность доказать EOF → `EnumerationIncomplete`, не пустая/успешная коллекция. Имена допускаются только canonical lowercase UUIDv4; каждый canonical directory кандидат перепроверяется no-follow, и **любой** отказ его повторного открытия (включая access/share/IO/unsupported) даёт `EnumerationIncomplete`, а не успешный частичный список. Известные из native attributes reparse/non-directory учитываются отдельно до попытки открытия; счётчики malformed/unsafe/reparse не публикуют имена или содержимое. Это не manifest/schema/hash validation, не durable receipt и не cleanup; подключение к startup/recovery — **NOT_WIRED**. Отдельно созданные `StagingRoot` имеют отдельные HANDLE; не считать стабильный scan snapshot при конкурентной модификации каталога другим процессом. Механизм не является sandbox от вредоносного процесса того же пользователя/admin. Diagnostics — только typed `SafeEvent` и bounded safe code. Junction и symlink различать: непривилегированный junction proof обязателен, symlink может дать точный NOT_RUN с raw OS code без elevation/Developer Mode/ACL changes. Проверки: `scripts/verify.ps1`, `scripts/verify-contracts.ps1` после обновления workspace boundary, raw exits и source/plan integrity сохраняются. Политика/ограничения: [ADR-003](../docs/adr/003-root-isolation.md).

# CORE — Codebase Memory, Serena и ast-grep

## Правило выбора

При работе с кодом используй Codebase Memory, Serena и ast-grep по их назначению,
а не заменяй исследование последовательным чтением больших файлов через grep/read.
Выбирай инструмент по вопросу; запуск всех трёх ради формального отчёта не нужен.
Документы, известные manifests, состояние файловой системы и запуск проверок
не требуют символьного поиска. Пока исходников нет, инструменты кода не заменяют
чтение спецификации и не могут подтвердить реализацию.

| Вопрос | Инструмент и первый шаг |
|---|---|
| Где реализовано неизвестное поведение, кто владелец? | Codebase Memory: `search_graph`, небольшой limit; `search_and_read_symbols`, если нужен и код |
| Как связаны владельцы, какой путь вызовов? | Codebase Memory: `read_symbol` с neighbors для прямых связей, `trace_path` для нескольких переходов |
| Известны имя символа или файл | Serena: `serena_find_symbol` либо `serena_get_symbols_overview` перед чтением целого source-файла |
| Что затронет изменение поведения/переименование? | Serena: `serena_find_referencing_symbols`; Codebase Memory: `detect_changes` для уже существующего diff |
| Найти похожие вызовы/синтаксическую конструкцию | ast-grep: `ast_search` с конкретным паттерном, языком и узким путём |
| Найти точную строку в индексированном коде | Codebase Memory: `search_code`; read/rg для прямого подтверждения строк |
| Прочитать известный README, план или manifest | Прямое чтение файла |
| Доказать выполнение, гонку или порядок событий | Тест, безопасные логи/trace и воспроизведение; графа недостаточно |

## Последовательность исследования

1. Найди вероятного владельца через Codebase Memory. Для известного символа/файла
   начинай сразу с Serena, без повторного широкого поиска.
2. Проследи только нужные связи. Используй небольшие выдачи и глубину 2–3;
   несколько известных символов читай пакетно, не весь repository dump.
3. Уточни тело, декларацию и references через Serena. Перед изменением интерфейса
   найди реализации доступным инструментом; не предполагай единственный call site.
4. Для повторяющейся формы вызова используй ast-grep. Пример паттерна:
   `function_name($$$ARGS)`; сначала проверь его на известном положительном примере,
   затем расширяй scope. AST-совпадение — кандидат, не доказанная ошибка.
5. Подтверди критичные строки непосредственным чтением актуального worktree.
   Затем редактируй минимальный участок и проверь нужное поведение тестом.

Сокращённый graph/snippet сначала запроси с большим лимитом или `full_output`,
а не считай обрезанный фрагмент полным контрактом. Отсутствие совпадений не доказывает
отсутствие функции: проверь имя, область и актуальность индекса.

## Worktree, ограничения и fallback

- Убедись, что индекс относится к нужному checkout. Для Serena в worktree указывай
  точный абсолютный project path; не перенастраивай общий проект под текущую задачу.
- Не выдавай индекс main за содержимое dirty/worktree. Критичный путь и тело
  подтверждай на диске; результаты устаревшего индекса отмечай как ограничение.
- Если tool/backend недоступен, зафиксируй это и используй узкий read/rg fallback.
  Не устанавливай и не перенастраивай общие сервисы без разрешения.
- Поиск не даёт разрешения на массовое AST-rewrite/rename. Для изменений нужны scope,
  references, preview/diff и проверки; не применяй auto-fix ко всему дереву вслепую.
- Статический граф не доказывает порядок выполнения, delivery IPC, thread affinity,
  resource lifetime, отсутствие races или безопасность данных.

Используй реально доступные инструменты текущего окружения.
Их наличие не расширяет полномочия агента.

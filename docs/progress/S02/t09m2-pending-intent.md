# S02-T09m2 — pending capture-intent worker API (candidate)

Baseline: main `55a82b7`; only v4 existing `capture_intents` schema is used; immutable 0001–0004 unchanged. Independent read-only re-review PASS for this bounded API; this is not S02 acceptance.

The application port adds typed create/read inputs. SQLite worker owns all SQL through its bounded request queue; create starts `BEGIN IMMEDIATE`, probes Saved first without projecting metadata, then scopes pending by principal, request mode and a worker-computed domain-separated fingerprint of the real `CaptureRequest` (operation ID, typed target and trusted trigger). Identical pending content and IDs yields `Existing`, an owned same-request mismatch in caller content/IDs yields metadata-free `Conflict` after validating the stored row, a new operation yields `Created`, foreign/mismatched request and any Saved yields `Conflict` without metadata. Read only returns `Pending` for the matching owner/request; for matching owner/mode, a fingerprint outside both closed v1 trigger digests is corruption (`IntegrityFailed`), while the real alternate trigger is `Conflict`. Foreign owner or changed mode always receives safe `Conflict` without checking the fingerprint. Corrupt owned content is `IntegrityFailed`, not deletion or repair. The inserted planned timestamp is SQLite UTC inside the transaction, not manifest time. The pixel SHA-256 is a typed validated digest supplied by the caller; future host must compute it from the same retained RGBA bytes. No new canonical, record, asset, staging file or Saved receipt is created by this API; pending without stage is not recoverable. Existing `lookup_operation` is unchanged.
